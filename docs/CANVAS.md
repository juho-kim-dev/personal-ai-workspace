# PAW - Canvas

2026-10-29 최신 사용자 결정에 따라 Space 이름을 **PAW - Canvas**로 정정한다. 앞선 PAW - Nodes / pawn은 중간 명칭이며 현행 약칭으로 사용하지 않는다. `paw-canvas`는 이 문서에서 목표 Space를 가리키며 저장소·폴더·배포 주소를 이미 변경했다는 뜻이 아니다. 기존 구현의 출발 제품과 운영 이름은 Naid다.

## 목적과 정체성

**문서와 데이터를 펼치고, 관계와 현재 상태를 연결해 보는 시각적 작업 공간.**

Canvas는 사람이 직접 또는 AI와 함께 자료를 읽고 편집하고 연결하는 PAW Space다. Markdown 노트맵에서 시작해, PAW의 실제 객체·관계·상태를 탐색하는 그래프, 자유 배치 캔버스, 다이어그램·차트, 워크플로 설계로 확장한다. 원문을 사람이 읽는 표현과 AI가 다루는 구조를 함께 유지한다. 특정 확장자만으로 AI 이해가 보장되지는 않는다.

**현재 출발점은 Markdown 중심 노트맵**이다. 기존 편집기·링크·Graph·Canvas가 기반이지만, 범용 공통 객체 그래프나 PAW 전체의 실시간 상태 시각화가 완성된 것은 아니다. 장기 정체성을 Markdown 편집기 하나로 제한하지 않는다.

## 소개와 슬로건 제안

- 슬로건 제안: **생각을 펼치고, 관계를 잇고, 흐름을 보다.**
- 짧은 소개: **문서·데이터·작업의 관계와 상태를 시각적으로 탐색하고 구성하는 PAW의 작업 공간.**
- 영어 소개: **A visual workspace for exploring and composing documents, data, relationships, and workflows.**

Space 이름은 사용자 확정이며, 위 소개 문구는 그 방향에 맞춘 문서 제안이다. 모든 미래 기능을 현재 제공하는 것처럼 홍보하지 않는다.

## PAW의 공통 개념

PAW의 풀네임은 **Personal AI Workflow**, 제품 분류는 **모듈형 Personal AI Workspace**다.

| 개념 | Canvas에서의 의미 |
| --- | --- |
| Space | 사용자가 작업하는 웹앱: PAW - Canvas |
| Tool | 재사용 기능: Markdown Reader/Editor, Graph Viewer, Canvas Editor, 향후 Charts·Diagram·Workflow 도구 |
| Object | 다루는 대상: 문서·대화·자료·프로젝트·관계·보기 문서. Canvas의 화면 노드는 원본 Object의 표현일 수 있음 |
| Core | Space 간 같은 원본·판본·관계·권한을 식별하고 연결하는 공통 계약과 기반. 구현 위치나 단일 중앙 서버를 확정한 이름이 아님 |

Spaces와 Tools는 배타적인 제품군이 아니다. Office도 여러 편집 Tool을 가진 Space이며 Canvas의 Tool도 다른 Space에서 사용할 수 있다. 전체 목표 구성은 Wiki, Yarns, Library, Boards, Forum, Git, Office, Studio, Study, Canvas다. Studio는 향후 후보이며 10개 통합 제품이 완성됐다는 뜻이 아니다.

## 용도와 목표 사례

아래는 개발 목표와 참고 용도다. 이름을 언급한 외부 도구의 통합·호환·기능 동등성 완료를 뜻하지 않는다.

| 용도 | 사용 예 | 개발 경계 |
| --- | --- | --- |
| Markdown 노트맵·PKM | 노트를 작성하고 주제·출처·링크로 연결해 Graph에서 찾고 Canvas에 배치 | 당장 완결할 흐름. 본문과 배치 상태를 분리 |
| 마인드맵 | 아이디어를 가지·그룹으로 정리하고 노트와 연결 | 기존 카드·선은 기반. 전용 계층 편집·자동 배치는 별도 검증 |
| Graphify형 관계 탐색 | 문서·자료에서 추출한 연결을 탐색하고 원문 근거로 이동 | 원문에서 추출한 관계와 AI 추론을 구분; 형식·어댑터는 미확정 |
| Archify형 구조 설명 | 프로젝트·시스템의 구성, 의존과 데이터 흐름을 다이어그램으로 설명 | 수동 설계도와 실제 상태에서 파생한 보기를 구분 |
| PAW 객체 상태 보기 | Git 프로젝트, Wiki 설계, Yarns 논의, Library 근거, Forum 쟁점을 같은 관계망에서 확인 | 원본 조회·권한·갱신 계약 필요. 확인 시각과 오래된 상태를 표시 |
| LLM Wiki | AI가 원본 대화·자료를 읽고 근거가 있는 Wiki 문서·관계를 제안; Canvas에서 지식 구조 검토 | Wiki가 문서 정본을 관리하고 Canvas는 참조·시각화. 제안 검토와 충돌 처리는 미래 기능 |
| n8n형 워크플로 | 조사→분석→Wiki 작성→Office 출력의 단계·조건·입출력을 구성 | 흐름 편집과 실행을 분리. 범용 실행기·n8n 호환은 미구현 |
| 차트·Mermaid | 객체 집계의 막대·원·선 그래프, 문서의 구조도 | 데이터 조회·집계·지원 문법을 별도로 정의. 모든 보기의 양방향 변환을 약속하지 않음 |

## 다른 Space에서 재사용하고 임베드하기

**같은 원본을 참조하고 같은 Tool을 재사용하는 것**을 목표로 한다. 데이터 중복 방지와 구현 중복 방지는 서로 다른 과제다. 독립 배포가 앱별 원본 사본이나 그래프 구현을 반드시 요구하지 않는다. 공통 물리 DB, 모든 데이터의 Canvas 이전, 전역 양방향 동기화를 먼저 확정하지 않는다.

- **Wiki:** 문서에 Canvas의 관계 그래프를 임베드한다. 그래프는 원본 객체 참조와 필터·배치만 보관하고, 노드 선택 시 원문·지정 판본으로 이동한다. 별도의 Wiki 전용 그래프 엔진을 복제하지 않는 방향이다.
- **Git·Forum:** 같은 프로젝트의 설계 문서·이슈·토론·참고 자료를 공통 Graph Viewer로 표시한다. 임베드를 제거해도 원본 문서·관계가 삭제되지 않아야 한다.
- **Yarns·Library:** 보존된 대화나 외부 자료를 참조한다. Yarns의 스레드·판본·메시지 식별을 유지하고 원본 대화와 AI 분석 문서를 별개로 둔다. 대화 리더는 Yarns의 재사용 Tool로 연결하며 Canvas가 모든 리더를 소유하지 않는다.
- **Study·Office·Boards:** 같은 자료를 병렬 열람하거나 문서·Pin과 연결한다. 편집 사본·번역·출력물은 원본과 별도 객체로 만들고 파생 관계를 남긴다.

첫 임베드는 읽기 전용을 권장한다. 최소 참조 계약은 원본 담당 시스템, 안정적 객체 ID, 최신/고정 판본 선택, 선택적 문서 범위다. 보기에는 필터·배치·확인 시각을 둔다. 정확한 필드명·저장 위치·패키지·iframe 또는 컴포넌트 방식은 각 담당과 검토하며 이 문서에서 고정하지 않는다.

권한은 원본에서 검사한다. 비공개 객체를 공개 Wiki에 임베드해도 공개되면 안 된다. 삭제·접근 불가·네트워크 실패·갱신 지연을 구분하고, 오래된 캐시를 최신 원본으로 표시하지 않는다. 후속 편집 임베드는 관찰한 revision으로 저장하고 충돌 시 초안을 보존해야 한다. 공용 UI 코드 재사용만으로 공통 데이터 계약이 구현됐다고 표시하지 않는다.

## 현재 기반과 앞으로의 기능

2026-10-29 확인 기준. 공개 Canvas는 아직 이식·배포되지 않았다. 이 공개 branch의 실제 앱 준비는 Wiki이며 root 시제품 테스트는 Canvas 인수 근거가 아니다.

| 상태 | 범위 |
| --- | --- |
| 기존 Naid main의 기반 | Markdown 편집/읽기, 파일·탭·분할·검색·링크, 공유 초안·revision 충돌 방지·복구, 파일/태그/링크 Graph, Canvas 카드·연결·저장과 카드 내부 전체 노트/제목/블록 편집, MCP/WebMCP |
| 기존 제품의 미병합 작업 | 고급 웹뷰어와 Canvas 선택 카드 복제. 공개판에 포함됐다고 표시하지 않음 |
| 먼저 완결할 흐름 | Markdown 노트맵의 문서·Graph·Canvas 참조 일관성, 저장·복구·이름 변경·삭제 검수 |
| 새로 개발할 연동 | 공통 객체·의미 관계·출처 계약, 재사용 Viewer와 Space 간 임베드, PAW 실제 상태 조회/갱신, AI 제안 검토 |
| 이후 확장 | 일반 JSON/동적 객체, Mermaid·차트·구조 시각화 어댑터, 워크플로 실행 |

기존 파일 카드 임베드는 Space 간 임베드가 아니며 Graph의 선은 범용 의미 관계 모델이 아니다. Canvas JSON 지원은 일반 JSON 객체 편집기가 아니다. 기존 API는 LLM Wiki 생성·검토나 범용 자동 실행기의 완성 근거가 아니다. 기존 제품 소스·배포·브라우저 검증 시점을 구별하고 공개 이식 시 기능·권한·브라우저 검증을 다시 기록한다.

## 권장 개발 순서와 완료 조건

다음은 구현 제안이며 일정이나 확정된 세부 스키마가 아니다. 기존 파일·알 수 없는 필드·초안·이력은 보존한다.

1. **Markdown 노트맵 한 흐름 완결:** 작성→링크→Graph 탐색→Canvas 배치→같은 원문 편집→저장·재접속·복구를 검수한다. 문서/부분 참조와 보기의 최소 계약부터 정한다. 같은 문서를 여러 카드로 보아도 본문을 복제하지 않고, 이름 변경은 참조를 유지하며 삭제는 끊김으로 표시한다. Canvas의 배치선과 문서의 의미 관계를 자동 동일시하지 않는다.
2. **Wiki 읽기 전용 임베드 한 사례:** 합성 Markdown 문서와 관계를 Canvas와 Wiki에서 같은 Viewer로 표시한다. 원문 변경 후 두 보기의 일치, 고정 판본 유지, 권한 거절, 원본 삭제, 갱신 실패를 확인한다. 하나의 관계를 여러 화면에 표시해도 중복 등록하지 않는다. 거대한 Core부터 만들기보다 이 사례에 필요한 최소 공통 참조를 검증한다.
3. **다른 Space의 실제 객체 연결:** Yarns 원본 논의·Wiki 문서·Library 자료·Git 프로젝트를 점진적으로 연결한다. 초기에는 명시적 새로고침/상태 조회로 정확성을 증명하고 이후 이벤트 갱신을 검토한다. 출처·방향·원문 추출/수동/AI 제안 관계를 구분한다.
4. **AI 지식 정리와 보기 확장:** LLM Wiki의 근거·기준 revision·변경 diff를 가진 제안을 승인/거절한다. JSON 구조화 보기·편집, 동적 객체, Mermaid·차트, Archify/Graphify형 산출물 어댑터는 지원 범위별로 추가한다. 기존 Canvas JSON 형식을 일반 JSON 편집 지원으로 계산하지 않는다.
5. **실행 가능한 워크플로:** 실행 권한·입출력·취소·재시도·중복 실행 방지·실행 이력을 갖춘 별도 단계로 검증한다. 선을 그리거나 그래프를 열기만 해도 외부 작업이 실행되는 구조를 피한다. AI는 필요한 API/MCP를 직접 사용할 수도 있으며 Canvas를 모든 자동화의 필수 관문으로 만들지 않는다.

공개판 준비는 위 미래 기능 전체를 기다리지 않고 기존 실제 앱의 확인된 범위부터 진행할 수 있다. 비공개 운영 데이터와 분리된 새 공개 인스턴스, 접근 정책·방문자 격리·브라우저 검증이 필요하다. PAW 내부 재사용은 승인된 동일 환경 안의 연동이며 비공개 운영 저장소를 공개판과 공유한다는 뜻이 아니다. Wiki는 기능하는 위키와 확인된 앱 주소를 잇는 허브로 유지하며 별도 PAW 안내 앱을 만드는 작업으로 확대하지 않는다.
